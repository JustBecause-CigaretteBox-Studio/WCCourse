第 1 小节

从 Excel 到数据库

很多同学第一次管理数据会用 Excel：把信息一行一行填进表格，查找靠「Ctrl+F」，统计靠公式。当数据只有几百行、一个人维护时，这完全没问题。

但程序要处理的数据往往更多、更复杂。想象一下学校教务系统：几万名学生、几十万条成绩、选课记录、考勤记录……如果全放在一个 Excel 文件里，打开会慢，多人同时修改会冲突，一不小心还会把公式拖错。

数据库就像一座由专业管理员看管的仓库。它知道每样东西放在哪，能按条件快速找到，还能防止两个人同时改同一条记录把数据搞乱。

Excel vs 数据库 的比喻
# Excel：像一本笔记本，翻开就能看，适合个人小数据
# 数据库：像图书馆的检索系统 + 书架 + 管理员，适合大量、结构化数据
第 2 小节

数据量与查找速度

Excel 查找是「从头到尾看一遍」，数据量越大越慢。数据库则会给常用的列建立索引（Index），就像字典前面的目录，能直接跳到目标位置。

比如要在 100 万条快递单号里找某一个单号，Excel 可能要翻很久，而数据库借助索引能在毫秒级返回结果。

索引的比喻
# 没有索引：从第一页翻到最后一页找人名
# 有索引：先查拼音目录，直接翻到那一页

索引也不是越多越好。每多一个索引，写入数据时就要多花一点时间维护。所以通常只给经常用来查询的列建索引。

第 3 小节

一致性与多人协作

数据库还有一个核心优势：保证数据一致性。例如，你可以规定「学生表里的学号不能重复」，数据库就会拒绝重复录入；可以规定「成绩必须是 0~100 之间的数字」，数据库会拒绝不合理的值。

这些规则叫做约束（Constraint）。它们让程序更可靠，也减少了人工检查的工作量。

数据库约束示例
-- 学号唯一，不能为空
student_id TEXT PRIMARY KEY NOT NULL UNIQUE,
-- 成绩在 0 到 100 之间
score INTEGER CHECK(score >= 0 AND score <= 100)

当多个用户或程序同时访问数据库时，数据库还会通过事务（Transaction）保证「要么全部成功，要么全部失败」，避免改到一半出错的尴尬局面。

什么意思呢？想象你在银行 App 上转账 1000 元。数据库至少要干两件事：先从你的账户扣 1000，再往对方账户加 1000。这两步必须一起完成。如果刚扣完你的钱，系统突然崩溃，或者网络断了，对方的钱还没加上——这 1000 元就凭空消失了。更麻烦的是，如果这时候有人查账，会看到"你的钱少了，对方的钱却没多"这种诡异状态。

第 4 小节

综合实战：把成绩单设计成数据库表

从 Excel 表格到表结构

假设你手里有一张 Excel 成绩单，包含：学号、姓名、语文、数学、英语。如果改成数据库表，可以怎么设计？

成绩表设计
CREATE TABLE scores (
    student_id TEXT PRIMARY KEY,  -- 学号，唯一标识一个学生
    name       TEXT NOT NULL,      -- 姓名
    chinese    INTEGER CHECK(chinese BETWEEN 0 AND 100),
    math       INTEGER CHECK(math BETWEEN 0 AND 100),
    english    INTEGER CHECK(english BETWEEN 0 AND 100)
);

动手任务：试着把身边的一个小表格（例如班级通讯录、个人书单）画成数据库表，标出主键（能唯一标识表中每一条记录、不可重复且不能为空的字段）、哪些列不能为空、哪些列需要限制取值范围。

第 1 小节

愿望 ≠ 需求

很多人学编程的第一步是：「我想做个 APP」。但这句话和「我想做道菜」一样，太模糊了——做什么菜？给谁吃？辣不辣？

在项目管理里，我们要把「愿望」翻译成需求。需求 = 用户真正想解决的问题，而不是用户嘴上说出的方案。

愿望 vs 需求
愿望：我想做个背单词 APP。
需求：用户想在碎片时间里记住 50 个新单词，并能检测记忆效果。

好的需求描述的是「谁在什么场景下想达成什么目标」。它让我们知道该做什么功能，不该做什么功能。

第 2 小节

5W1H 提问法

面对模糊的想法，最有效的工具是 5W1H。像记者一样连续追问，把空泛的愿望变具体。

5W1H 提问清单
Who：谁用？（小学生 / 成人 / 老师）
What：做什么？（生成题目 / 计时 / 打分）
When：什么时候用？（课前练习 / 睡前复习）
Where：在哪里用？（教室电脑 / 家里手机）
Why：为什么需要？（提高口算速度 / 减轻家长出题负担）
How：怎么用？（输入年级 → 选择题量 → 开始答题）

每个问题都能帮你砍掉一厢情愿的功能。例如如果用户只在手机上用，你就可以先不考虑不同尺寸屏幕的打印排版（如果不考虑某些奇形怪状的手机屏幕）。

第 3 小节

把需求变成功能清单

问完 5W1H，下一步是把答案整理成功能清单。清单里的每一项都应该是可验证的。

什么叫“可验证的功能”？

可验证的功能是指那些可以通过具体的测试用例来验证其是否正常工作的功能。例如，“用户可选择年级”这个功能，我们可以通过测试不同的年级选项来验证它是否正常工作。“界面美观”就不是可验证的功能。

功能清单
1. 用户可选择年级（1-3 年级）。
2. 根据年级生成 20 道加减法口算题。
3. 用户输入答案后自动判分。
4. 显示正确率与用时。
5. 支持重新生成一套新题。

这份清单就是后续写代码的「合同」。凡是不在清单里的功能，比如排行榜、换皮肤，都可以先放一放。

这套方法不是万能的

在游戏，以及其他一些更注重艺术性而非实用性的项目里，未必适合一上来就列功能清单——氛围、美感、手感这些东西很难拆成一条条可验证的条目，你没法把「这个画面要让人感到孤独」写成需求。

这类项目的头脑风暴阶段往往是另一番景象：你可能先画几个图标、定一套配色，或者先写一段音乐，用这些东西激发灵感，摸索出「感觉对了」的方向。等到真正开始写代码、要实现某个具体系统的时候，才回到「功能清单」这种思路上来。

还有一点更重要：所有讲思路的教程（包括这一篇），都只是给你提供灵感，而不是给你划定边界。如果你的想法和教程说的不一样，那就先按你自己的想法试试。方法是为项目服务的，不是让项目去迁就方法。

在本课程包中，你还会学到流程图、伪代码，教程都给出了一种推荐的格式，但是是否要按照教程来由你自己决定。

第 4 小节

综合实战：澄清「口算题生成器 2.0」的需求

把本模块内容用起来

假设我们要把第一阶段做过的「口算题生成器」升级成 2.0。第一步不是写代码，而是先澄清需求。

5W1H 填空练习
Who：小学一至三年级学生或家长。
What：自动生成口算题、答题、判分、错题回顾。
When：每天放学后练习 10 分钟。
Where：家用电脑或平板。
Why：巩固计算能力，减少家长手动出题时间。
How：选择年级和题量 → 生成题目 → 答题 → 提交 → 看结果。

试着自己先写一个功能清单，然后从里面挑出 3 个最核心的功能。
